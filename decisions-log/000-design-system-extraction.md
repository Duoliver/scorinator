# Task 0 — decisions log: design-system extraction

Judgment calls made while building `design-system/` (tokens + primitives) that a later session shouldn't silently re-litigate. Condensed here from `PROGRESS.md`'s running Decisions log at the end of the Task 0 session — see `PROGRESS.md`'s Decisions log section for the procedure this follows, and `progress-reports/000-design-system-extraction.md` for the task's overall report.

- **2026-09-03:** `Input` moved from a fully controlled `value`/`onChange` API to **controlled-but-isolated**: the field owns its value in its own internal state (typing re-renders only `Input` itself, never a parent/form) and exposes it via a `ref` carrying a `FieldHandle<string>` (`getValue`/`setValue`/`subscribe`/`focus`, defined in the new shared `src/design-system/field.ts`) instead of a `value` prop. `Select`/`Checkbox`/`Switch` are **not** migrated yet — deferred to a follow-up task once this pattern's proven; they keep their existing controlled APIs for now.
  - **`ref` requires `forwardRef` from `preact/compat` here** — empirically confirmed a plain `ref` prop does not reach a Preact function component in this project's Preact 10.29.8 + Vite/TS setup (tested directly; a bare `{ ref }` destructured from props stayed `null`). A differently-named prop (e.g. `fieldRef`) would have avoided needing `preact/compat` entirely (also confirmed working), but the team wants JSX-conventional `ref=` ergonomics, so `preact/compat` was pulled in deliberately — first use of it anywhere in this codebase.
  - **`subscribe(listener)`** (returns an unsubscribe fn) is the answer to "how do other fields conditionally render off this one's value without re-rendering the whole form" — it fires on every value change regardless of origin (typed or an imperative `setValue()`), so a subscriber always sees the current value. This is deliberately *not* deferred to a future form engine: it's a small, self-contained per-field primitive (a `Set` of listeners in a `useRef`) that a later form engine would most likely be built on top of, not replaced by. No schema/registry/validation/dirty-tracking was added — those stay deferred.
  - **`onChange` vs `subscribe`**: `onChange` fires only on real user interaction (typing); an imperative `setValue()` does **not** call it — mirrors how a controlled `<input>`'s `value` changing from outside never fires its own `onChange`. `subscribe` is the channel for "the value is now X, however it changed." Verified in both directions by test.
  - **`setValue()` writes the DOM node directly** (`inputEl.current.value = next`) in addition to calling the internal `useState` setter — Preact's state updates are batched/async, so without the direct write, a `getValue()`/DOM-assertion immediately after `setValue()` could observe the pre-update value. This was caught by a failing test, not anticipated in the design.
  - `commitValue` (the single internal function both typing and `setValue()` route through) is wrapped in `useCallback` with the latest `onChange` held in a ref (`onChangeRef`), giving it a permanently stable identity — needed to satisfy `react-hooks/exhaustive-deps` on `useImperativeHandle`'s dependency array correctly rather than suppressing the warning.

- **2026-09-03:** Built `Checkbox` and `Switch` as new primitives (`design-system/components/{Checkbox,Switch}/`), both following the same accessible pattern: a real `<input type="checkbox">`, visually hidden (`position:absolute; opacity:0`, not `display:none`, so it stays focusable/keyboard-operable) but wrapped in a `<label>` alongside a decorative box/track span, with the checked-state visuals driven purely by a `.input:checked ~ .box` CSS sibling selector rather than duplicating the boolean into a second JS-rendered conditional. `Switch`'s input additionally carries `role="switch"` (ARIA APG's toggle pattern). A few things a later session shouldn't re-litigate:
  - `label` is a **required** prop on both (unlike `Input`/`Select`, where it's optional) — there's no placeholder-text fallback for a checkbox's accessible name, so an unlabeled instance would be inaccessible by default.
  - The checkbox's checkmark is CSS-generated content (`.box::before { content: '✓' }`), not a JSX text node — putting it in the DOM as real text made it leak into `@testing-library`'s label-text computation (even under the decorative span's `aria-hidden`), breaking `getByLabelText` on an exact string match.
  - Box/track/knob dimensions (22px checkbox, 52×26px track, 18px knob) are literal `rem` values, not built from `--space-*` — those tokens are reserved for padding/gap/font-size per `coding-standards.md`; a control's own intrinsic size isn't in that category. The gap between control and label (10px in the reference) **is** a `gap` value, so it does use a token — rounds up to `--space-3` (12px) per the existing tie-round-up rule (8px/`--space-2` and 12px/`--space-3` are equidistant).
  - Neither gets a hover/press box-shadow or a CSS `transition` — the Foundations reference shows neither for these controls, and adding either would be inventing style not specified (and would break from `Button`'s instant, transition-free neobrutalist feel).
- **2026-09-03:** Task 0 was marked done but review against the Foundations reference's "Inputs" section found the numeric input and `Select` missing/inert — fixed under this same task rather than a new `PROGRESS.md` row:
  - **Number input** stayed inside `Input` rather than becoming its own component — it's still the same `<input>` element, just needing conditional styling (`.input[type='number']`: `font-mono`, centered, tighter padding) plus `min`/`max`/`step` props. `onChange` deliberately still reports a `string` (matches `Input`'s existing contract; numeric consumers `Number()` it themselves) rather than widening the callback signature.
  - **Select** became its own primitive (`design-system/components/Select/`) since it's a different DOM element and prop shape (an `options: {label,value}[]` list, not free text) — matches the one-primitive-per-folder convention every other component follows. It duplicates `Input`'s `.field`/`.label` CSS rather than factoring out a shared `Field` primitive; no such shared primitive exists yet and introducing one wasn't asked for. A `placeholder` renders as a `disabled hidden` first `<option>` — standard native-select placeholder pattern.
  - `Checkbox`/`Switch` (also shown in the same Foundations reference section) are explicitly deferred to a follow-up task — not built here.

- **2026-09-02:** `Tabs` owns its active-tab state internally (`defaultTab` + `content` per tab, switches and renders the panel itself) instead of being externally controlled (`activeId`/`onChange` from the caller) — content-switching is the component's core expected behavior, so every consumer shouldn't have to reimplement the same conditional. Kept an optional `onChange` (fires on every switch, e.g. for lazy-loading a tab's data) but deliberately did **not** add a controlled `activeId` override — the one case that needs it (an external actor, e.g. browser back/forward via a route param, forcing the visible tab without a click) isn't a need anywhere in the app yet; add it later if that materializes rather than building the escape hatch preemptively.
- **2026-09-02:** `--color-fg-muted` (#5C5C5C) is kept as-is despite measuring ~6.69:1 on `--color-surface` (short of the Foundations screen's claimed blanket AAA 7:1) — confirmed with the user it's for disabled/de-emphasized elements only, not primary text. See `docs/design-reference/README.md`'s "Known contrast exception" note.
- **2026-09-02:** 16-colour team palette shown in the Foundations screen was deliberately _not_ extracted into `design-system/` tokens — it's explicitly captioned "placeholder... pending final review" and is MVP3 scope. Extract it when MVP3 is approved, not before.
- **2026-09-02:** Styled `design-system/` primitives with plain CSS Modules (Vite's built-in `*.module.css` support) rather than Tailwind. `CLAUDE.md` lists Tailwind in the tech stack, but it isn't installed/configured anywhere in the repo — wiring it is a separate decision, out of scope for this task.
