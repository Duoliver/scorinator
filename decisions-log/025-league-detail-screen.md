Planned with the user first (three calls confirmed before build: add a `slug` field for routing, match the prototype's two-tab layout exactly rather than the status board's three-tab wording, and redirect here straight off League Setup's Create button, ahead of Task 24).

  `LeagueRecord` (`features/leagues/types.ts`) gained a `slug: string` field. `addLeague` (`app/state/leagueStore.ts`) rolls it from the league name with `engine/identity`'s `slug()`, the same call `TeamForm` already makes for a team name. `slug()` throws a `RangeError` for a degenerate name (blank, or symbols-only like `"!!!"`). `TeamForm.handleSave` already guards this for a team name, with its own fixed copy rather than the thrown message, since that message hardcodes the words "team name". `LeagueSetupScreen`'s Review step disable check only caught a blank name, not a symbols-only one, so wiring `slug()` into `addLeague` opened the same gap for a league. Closed it the same way: `handleCreate` wraps the `addLeague` call in a try/catch, showing "Enter a league name with at least one letter or number." on failure, matching `TeamForm`'s pattern and copy.

  New `src/features/leagues/LeagueDetailScreen.tsx`, a sibling to `LeagueSetupScreen.tsx` in the same screen folder — not a new top-level module, matching how `steps/` already lives there. Routing-agnostic, per `module-boundaries.md`: it takes a plain `slug` prop, not a route param. Renders a "League not found" message for an unknown slug, otherwise the league name, a meta line (team count, home advantage, points, and the hardcoded string `"Round robin (two-way)"` — the only fixture format `engine/fixtures` generates today, no field stores a format name), a "← Leagues" link, and a `Tabs` with two tabs, Standings and Fixtures, each holding a plain placeholder. No fake data, no Task 14/15/16 work pulled forward.

  `app/routes.ts` gained `ROUTES.leagueDetail` (`/leagues/:slug`, the route pattern `<Router>` matches) and `leagueDetailPath(slug)` (the real URL to navigate to). `AppShell.tsx` gained a `LeagueDetailRoute` adapter — the first of the three route adapters that actually forwards a prop (`slug`, the one param `preact-router` injects) instead of ignoring it. Nav highlighting needed a small fix alongside it: a `/leagues/<slug>` URL never exact-matches `ROUTES.leaguesNew`, so the `Leagues` nav item now matches on any path starting with `/leagues/`, not just an exact one.

  `LeagueSetupScreen.handleCreate` now calls `route(leagueDetailPath(league.slug))` on success, instead of resetting the wizard to step 1 in place with a success toast. One ordering subtlety, worth a note for later: the existing unmount effect (`LeagueSetupScreen.tsx:44-58`) reads local state through `latestRef`/`detailsStepRef` and writes it back into `leagueDraftStore` on a real unmount, which `route(...)` now triggers. The four local-state-reset lines that used to just put the visible wizard back at step 1 also still run, in the same order, immediately before the `route()` call — removing them would leave local state stale at unmount time, and the cleanup effect would silently push that stale draft back into the store, undoing the `reset()` call two lines above it. `status` stays in the component, but only for the new error path — a successful create shows no toast now, since the screen navigates away.
