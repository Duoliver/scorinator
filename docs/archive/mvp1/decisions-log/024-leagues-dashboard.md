  A real finding, not a plan item: `+ New League`, `Open standings`, and `LeagueDetailScreen`'s existing back-link all work as plain `<a href>` tags, no `onClick` needed. Reading `preact-router`'s own source confirmed it: mounting any `<Router>` (`AppShell` already does) attaches one global click listener that intercepts every same-origin `<a href="/...">` click and routes it client-side. `AppShell.tsx`'s own nav links already call `route()` by hand on click, which still works, just redundantly — not touched here, since it is unrelated to this task. `LeagueSetupScreen`'s `handleCreate` (Task 25) genuinely does need its explicit `route()` call, since that is an imperative post-submit navigation with no click for the router to intercept.

  `app/routes.ts` gained `ROUTES.leaguesDashboard` (`/leagues`). `AppShell.tsx` gained a `LeaguesDashboardRoute` adapter (routing-agnostic, no props, same shape as `TeamsRoute`), registered at that path, and `NAV_ITEMS`'s `Leagues` entry now points there. `isNavItemActive` (from Task 25) needed widening too — it matched only `/leagues/...`, missing the new bare `/leagues` path.

  A real regression turned up while manually verifying this task, in code Task 25 shipped, not in anything built today. The steps: create a second league back-to-back, through `+ New League` → wizard → create → dashboard → `+ New League` again. This opened the wizard back on the Review step. It showed the *previous* league's name and team. `LeagueSetupScreen.handleCreate` reset local state and the draft store, then called `route(...)`, in that order. This looked right. But Preact batches a same-tick `route(...)` together with a component's own pending `setState` calls. It can unmount a component without ever re-rendering it with those pending updates first. `latestRef.current` (read by the unmount effect that persists draft state) is only ever refreshed inside the render body. So it stayed pinned to the stale pre-create values, and the unmount effect dutifully wrote them straight back over the `reset()` call two lines earlier. Fixed with a `suppressDraftSyncRef` flag: `handleCreate` sets it before resetting the store and navigating. The unmount effect skips its own write entirely when it sees that flag set, instead of trying to out-race a batching guarantee Preact does not make. This let `handleCreate` drop its four now-pointless local-state-reset lines too — the component never renders again either way. New regression test in `LeagueSetupScreen.test.tsx`, which forces a real unmount via `cleanup()` right after a mocked `route()` call, the exact sequence that reproduced the bug.

  295 tests (13 new), `type-check`, `lint`, and `build` all stay clean. Verified end to end the same Playwright-against-`vite preview` way as Tasks 25 and the Drawer fix: create a team, create two leagues back to back through the dashboard, confirm both cards render correctly, confirm the second wizard visit opens clean rather than showing the first league's stale data, confirm `Open standings` and the `Leagues` nav highlight both work. - **2026-09-15 (fix — missing hover/active states):** The user reported two real bugs. `+ New League` had no hover or click feedback. `Open standings` had no hover feedback. Both anchors, in `LeaguesDashboardScreen.module.css`, had only their resting styles copied from the prototype — its `style-hover` rules never made it across.

  Fixed by adding the missing rules. Each one matches its own established source exactly, not a new pattern. `.newLeagueLink` gained `:hover` and `:active` rules matching `Button`'s own `.md` size class (`Button.module.css`) — the same lift-and-shadow, press-in feel every other accent button in this app already has. `.openLink` gained an `:hover` rule matching the invert pattern `Drawer`'s `.close` button already uses (`background: var(--color-fg); color: var(--color-surface)`). This is also the prototype's own exact hover rule for this element. `.newLeagueLink` also gained `display: inline-block`. Reason: `transform` does not reliably apply to a default-inline anchor, the same reason `Button` itself uses `inline-flex`.

  Verified with computed styles through the same Playwright-against-`vite preview` approach used elsewhere this session, hovering each element and reading `transform`/`box-shadow`/`background` before and after. 295 tests, `type-check`, and `lint` all stay clean — no test coverage added, since these are pure `:hover`/`:active` CSS states with no jsdom-visible behavior to assert on.

  Flagged, not fixed: `LeagueDetailScreen`'s `← Leagues` back-link (`.backLink`) has no color or hover rule of its own either — it renders in the browser's plain default link color today. Same root cause, a different link, not something the user reported this time. Left for a follow-up.

- **2026-09-15 (follow-up — extract Button styling for link-shaped actions):** The user pointed out the previous fix duplicated CSS by hand instead of reusing it: `.newLeagueLink` copied `Button`'s `primary`/`md` look, `.openLink` copied a bordered, invert-on-hover look `Drawer`'s `.close` button already had too. Asked to extract it, for reuse across both buttons and links.

  `Button` (`design-system/components/Button`) now takes an optional `href`. When set, it renders an `<a href>` instead of a `<button>`, through the exact same `class={...}` string, so it shares its CSS module with zero rewriting. `type`/`disabled` stay `<button>`-only — an `<a>` has no native disabled state, and no current `href` caller needs one; left unsupported on purpose rather than building `aria-disabled` handling nobody asked for.

  New `outline` variant, alongside the existing `primary`/`secondary`/`destructive`/`ghost`: bordered, no shadow, inverts to `background: var(--color-fg); color: var(--color-surface)` on hover — the exact look `Open standings` needed, and the one `Drawer`'s `.close` button already carries. Confirmed with the user before building: cover both duplicates, not just the exact-match one (`+ New League`, which needed no new CSS, only `Button`'s `href` mode). `Drawer`'s `.close` itself stays on its own local style, a call made on purpose, not an oversight — it is a small fixed-size icon button, a different shape than `Button`'s size scale models, not worth forcing into it.

  `LeaguesDashboardScreen.tsx` now renders `<Button href={ROUTES.leaguesNew} variant="primary" size="md">` and `<Button href={leagueDetailPath(league.slug)} variant="outline" size="sm">` in place of the two raw, hand-styled anchors. `LeaguesDashboardScreen.module.css` lost `.newLeagueLink` and `.openLink` entirely, hover/active rules included — both fully dead code now.

  298 tests (3 new in `Button.test.tsx`, covering the link mode and the new variant), `type-check`, `lint`, and `build` all stay clean. `LeaguesDashboardScreen.test.tsx` needed no changes — `Button`'s link mode still renders a real `<a href>`, so its existing `getByRole('link', ...)`/`toHaveAttribute('href', ...)` assertions kept passing unchanged, confirmed by running them rather than assumed. Verified visually too, the same Playwright-against-`vite preview` way as the hover fix this task followed: both links show identical hover/active behavior as before, this time reading it off shared `Button` CSS.
