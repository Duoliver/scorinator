# Task 13 — League Setup screen

**What was built:** `features/leagues` holds `LeagueSetupScreen`, a 3-step wizard (Details, Teams, Review). Details takes a league name, win/draw/loss points (defaulting from `DEFAULT_POINTS_CONFIG` in `engine/standings`), and a home-advantage switch. Teams lists the shared team roster with a search box and a checkbox picker, plus a "+ Create new team" drawer that reuses `TeamForm`. Review shows a read-only summary and a "Create league" action. `App.tsx` mounts `LeagueSetupScreen` under `TeamsScreen`, the same ad hoc way as before.

Two new supporting pieces went in alongside the screen:
- `features/components/` — a new folder holding `TeamForm` (moved out of `features/teams/`) and the `TeamRecord` type it needs. `features/leagues` and `features/teams` both import from here now, instead of `features/leagues` importing `features/teams` directly. `src/features/FEATURES.md` documents the rule: `features/components/` never imports from a screen folder, only the reverse.
- `app/state/` — two Zustand stores. `useTeamsStore` holds the one shared, in-memory team roster. `useLeagueStore` holds the created-league list. `TeamsScreen` now reads and writes through `useTeamsStore`, instead of its own local state. This means a team created on either screen shows up on both, in the same session. `useLeagueStore().addLeague()` rolls the OVR for each selected team once, at league creation, using `rollOVR` (`engine/tier-ovr`) and a freshly seeded `Rng`.

**Test approach:** This task used Testing Library integration tests, per the `features/` row of `tdd.md`. It added one test file per step component, plus a full-wizard `LeagueSetupScreen.test.tsx`. Both match the style of `TeamsScreen.test.tsx`. `app/state/teamsStore.ts` and `leagueStore.ts` got plain unit tests against the store directly, using `getState()`/`setState()`. One of those checks that a rolled OVR always lands inside the Tier range for its team. `TeamsScreen.test.tsx` gained a `beforeEach` that resets `useTeamsStore`, since the store is now a module-level singleton shared across tests. 252 tests pass repo-wide. `type-check` and `lint` both come back clean.

**Decisions made:** Six calls, confirmed with the user before and during the build. Full detail lives in the 2026-09-10 entry of the decisions log in `PROGRESS.md`:

3. Built the 3-step wizard from the design-reference prototype, not a single-page form.
4. MVP1 has no Season entity, so the league itself stands in for one. OVR rolls at league creation now, not deferred to fixture generation.
5. `TeamForm` and `TeamRecord` moved into a new `features/components/` folder, to avoid a cycle between `features/teams` and `features/leagues`. Rule and reasoning live in `src/features/FEATURES.md`.

One build-time-only finding, not a design call: Vitest externalizes `node_modules` packages by default. This skips the alias resolution Vite normally applies to them. As a result, the react-hook binding in Zustand failed to resolve the bare `react` import under test. `vite build` and the `preact/compat` alias both work fine outside tests. Fixed with `test.server.deps.inline: ["zustand"]` in `vitest.config.ts`.

**2026-09-10 addendum — `Tabs` gains an imperative ref API, wizard now uses `Tabs`:** The user asked for a way to switch the active tab of `Tabs` from outside the component, without lifting the active-tab state into the parent, then asked for the wizard in `LeagueSetupScreen` to use it.

`Tabs` (`design-system/components/Tabs`) now takes an optional `ref`. It is shaped as `FieldHandle<string>`, the same ref shape `Input`/`Select`/`Switch`/`Checkbox` already expose (`getValue`, `setValue`, `subscribe`, `focus`). This reuses that shape rather than inventing a new handle type just for this component. `getValue` returns the active tab id. `setValue` switches the active tab and its rendered content, the same as a tab-button click. It does not call `onChange`, though — this matches how the other fields already treat a programmatic `setValue` as distinct from user interaction. `subscribe` fires on every change, from either source. `focus` moves focus to the active tab button. Internals follow the same `commitValue`/`listenersRef`/`useImperativeHandle` shape `Input.tsx` already uses. One addition: a `Map` of tab-id to button element (`tabButtonsRef`), since `Tabs` renders more than one focusable control.

`LeagueSetupScreen` dropped its own `Step` type, `step` state, and hand-rolled row of stepper buttons. It now renders one `Tabs`. Each wizard step (`DetailsStep`/`TeamsStep`/`ReviewStep`) becomes the `content` of one `TabItem`, all driven by one `stepsRef`. Each step has its own Back/Next button, and each calls `stepsRef.current?.setValue(id)`. For example, the `onNext` handler in `DetailsStep` becomes `() => stepsRef.current?.setValue('teams')`. Neither step calls a `setStep` prop passed down from the parent anymore. The tablist buttons in `Tabs` (labelled "1 · Details" and so on) still give free-jump navigation between steps, the same as before. This now comes for free, as part of the primitive itself.

Test approach: `Tabs.test.tsx` gained four tests against the ref (`getValue` tracks a click, `setValue` switches the tab with no `onChange` call, `subscribe` fires on both a click and a `setValue`, `focus` moves focus to the active tab button). One of the four wraps its `setValue` call in `act` from `preact/test-utils`. That call sits outside a real DOM event, and Preact batches the resulting re-render onto a microtask. `userEvent.click` already handles this internally for the other tests, so only the direct-ref test needed it. `LeagueSetupScreen.test.tsx` needed no changes. It already drove the wizard through visible button clicks, which work the same way regardless of what sits behind them. 256 tests pass repo-wide, up from 252. `type-check` and `lint` stay clean.

**2026-09-10 addendum — inline-style cleanup:** `TeamsScreen`, `TeamForm`, `LeagueSetupScreen`, and all three step components lost every inline `style` prop. The one exception `coding-standards.md` allows stays: a colour swatch background, computed from the `colour` field of a team. Each gained a sibling `.module.css` file. A few literal values already matched an existing token exactly. Values with no exact token match stayed as literal `rem`, unrounded, since rounding them was not part of this pass. **2026-09-10 addendum — Select all in the Teams step:** `TeamsStep` gained a "Select all" / "Clear selection" toggle, next to the "N teams selected" line. It acts on whichever teams the search box currently shows. This surfaced a real staleness bug. Each `Checkbox` in a row is uncontrolled. A bulk change that only touched `selectedSlugs` in the parent would not visually check or uncheck the boxes. Fixed by keeping a `Map` of the `FieldHandle<boolean>` for each visible row, read from the ref `Checkbox` exposes. `.setValue()` runs on every affected row, alongside the state update. Five new tests in `TeamsStep.test.tsx`. 261 tests pass repo-wide, up from 256. Full detail in the matching 2026-09-10 decisions-log entry.
